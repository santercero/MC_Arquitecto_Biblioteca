RESUMEN_EJECUTIVO:
Se documenta la evolución del script SSJS "SSJS - SMS Opt Out Azure Transac" utilizado en producción en Norteamérica para procesar opt-outs SMS mediante integración API con Azure.

El script original presentaba errores de ejecución derivados principalmente de falta de validación de CUSTOMER_ID, construcción manual insegura del JSON, logging insuficiente, baja visibilidad de ejecución y manejo incompleto de errores.

La versión corregida implementa validación estricta de registros, construcción segura del payload usando arrays y join(), logging granular y estructurado, mayor trazabilidad mediante Write() y try/catch específicos por bloque crítico.

CONTEXTO_Y_PROBLEMA:
El proceso obtiene registros desde la Data Extension `DE_SMSStopTransac`, autentica contra Azure AD usando OAuth2 client_credentials, genera un bearer token, construye un payload JSON y envía los registros a `https://guessincnaprodapim.azure-api.net/CustomersNA/api/validation/phone-reply`.

El script original fallaba intermitentemente por registros con CUSTOMER_ID vacío y por construcción manual del JSON concatenando strings dentro del loop. Esto producía payloads inválidos, errores ocultos y baja trazabilidad.

SOLUCION_PROPUESTA:
Refactorizar el flujo SSJS manteniendo la lógica funcional original pero endureciendo validación, logging, construcción JSON, control de errores y trazabilidad.

DECISIONES_TOMADAS:
- Ignorar registros con CUSTOMER_ID vacío
- No detener el procesamiento global por registros inválidos
- Construir JSON usando arrays + join(',')
- Mantener OAuth client_credentials
- Mantener procesamiento batch único por ejecución
- Centralizar logs en DE_smsLog
- Añadir logging incluso para errores de logging
- Mantener Write() visibles para troubleshooting operativo
- Mantener status específicos por escenario
- Priorizar robustez y trazabilidad frente a simplicidad

PASOS_DE_IMPLEMENTACION:
1. Revisar payload generado por el script original
2. Detectar registros inválidos en DE_SMSStopTransac
3. Identificar CUSTOMER_ID vacíos
4. Refactorizar construcción JSON
5. Sustituir concatenación manual por payloadArray.join(',')
6. Añadir validación null, undefined, empty string y trim()
7. Añadir logging estructurado
8. Añadir Write() operacionales
9. Añadir manejo granular de errores
10. Registrar errores específicos de autenticación, ejecución, respuesta API y logging
11. Validar respuestas accepted/rejected de API
12. Desplegar en producción NA y verificar funcionamiento operativo

RIESGOS_O_ADVERTENCIAS:
- El client_secret sigue hardcodeado en el script
- HTTP.Post no implementa retry automático
- Posible timeout si aumenta mucho el volumen de registros
- Retrieve() sin filtro puede impactar rendimiento
- El payload final sigue construyéndose manualmente como string JSON
- No existe paginación
- No existe control de concurrencia
- No se marca Processed en la DE
- Riesgo de reprocesamiento si falla parcialmente
- Write() excesivos pueden dificultar lectura en ejecuciones masivas

BUENAS_PRACTICAS:
- Validar siempre claves funcionales antes de construir payloads
- Nunca concatenar JSON manualmente dentro de loops complejos
- Usar arrays + join() para payloads JSON
- Añadir logs específicos por tipo de error
- Capturar también errores de logging
- Añadir Write() durante fase de estabilización
- Separar autenticación y ejecución API en bloques independientes
- Registrar statusCode y body de respuestas no exitosas
- Evitar depender de Rows.length sin validar Rows
- Añadir controles null, undefined, empty y trim()
- Priorizar resiliencia parcial, los registros inválidos no deben bloquear el batch completo
